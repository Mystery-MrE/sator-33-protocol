# N-002: Raw Execution Observation Record

**Status: FROZEN**

N-002 defines a record of facts observed at a raw execution boundary. It does not classify an execution as accepted, rejected, passing, failing, correct, or incorrect. Qualification and policy decisions are outside this specification.

## 0. Requirements

### 0.1 Artifact preservation

**N-002-REQ-001:** An artifact record MUST contain `role`, `data`, `encoding`, and `digest` members.

**N-002-REQ-002:** The `role` member MUST identify the artifact's observed relationship to execution; it MUST NOT express a qualification decision.

**N-002-REQ-003:** For every artifact whose role is `supplied`, the implementation MUST preserve the exact byte sequence delivered to the raw execution boundary. The supplied byte sequence MUST be recoverable from the artifact representation such that `decode(data, encoding) == supplied_bytes`. Here, `supplied_bytes` is a defined byte sequence, not an artifact-record member.

### 0.2 Digest binding

**N-002-REQ-004:** Every artifact MUST contain a SHA-256 digest with `byte_domain` equal to `artifact_bytes`.

**N-002-REQ-005:** For an artifact digest whose `byte_domain` is `artifact_bytes`, the digest MUST be computed over exactly the byte sequence obtained by decoding that artifact's `data` according to its `encoding`.

## 1. Record model

An N-002 record contains observed completion facts, zero or more artifacts, and optional context. The following shape is illustrative; optional members are marked accordingly:

```json
{
  "artifacts": [
    {
      "role": "stdout",
      "data": "example output",
      "encoding": "raw",
      "digest": {
        "algorithm": "sha-256",
        "byte_domain": "artifact_bytes",
        "value": "<lowercase hexadecimal SHA-256>"
      }
    }
  ],
  "completion": {
    "exit_code": 0
  },
  "environment": {
    "locale": "C.UTF-8"
  }
}
```

The digest source is unambiguous:

```text
data -> decode(data, encoding) -> artifact_bytes -> SHA-256 -> digest.value
```

`artifact_bytes` denotes the decoded byte sequence for an artifact. It is not an additional JSON member. A digest MUST NOT be computed over parsed or reserialized objects, filesystem metadata, artifact names, transport framing, encoded strings, or derived representations.

## 2. Artifact transport representations

The `encoding` member MUST identify one of the N-002-defined transport representations: `raw`, `base64`, or `hex`. `encoding` describes only the representation of `artifact_bytes`; it does not describe their semantic type, format, validity, or meaning.

`decode(data, encoding)` is defined as follows:

* `raw` represents a Unicode string encoded as UTF-8. `data` MUST be a JSON string containing only Unicode scalar values other than U+0000, and `artifact_bytes` is its UTF-8 encoding. Producers MUST use `base64` or `hex` for arbitrary bytes, including NUL bytes or byte sequences that are not valid UTF-8. JSON escape syntax is transport syntax for the string and does not itself represent byte escapes.
* `base64` represents the bytes obtained by strict RFC 4648 base64 decoding of the JSON string in `data`. The standard alphabet and required padding apply; whitespace and non-alphabet characters are forbidden.
* `hex` represents the bytes obtained from pairs of lowercase hexadecimal digits in the JSON string in `data`. The string MUST have even length; uppercase digits, whitespace, prefixes, and separators are forbidden.

An artifact's `data` MUST be a JSON string. An implementation MUST reject an artifact whose `encoding` is not defined above or whose `data` does not satisfy the selected representation.

## 3. Observation boundaries

### 3.1 Supplied bytes

For an artifact whose `role` is `supplied`, `supplied_bytes` denotes the exact byte sequence delivered to the raw execution boundary before parsing, decoding, text conversion, or normalization. The artifact's `data` member, decoded according to `encoding`, MUST reproduce those bytes:

```text
decode(data, encoding) == supplied_bytes
```

### 3.2 Environment

`environment` is an optional capture of producer-observed runtime state associated with raw execution. The role `environment` identifies captured runtime-state bytes. It does not assert that those bytes constitute a causal explanation, policy input, or semantic interpretation.

An environment value MUST represent state directly observed by the producer and MUST NOT represent an inferred cause, interpretation, policy judgment, execution result, or qualification decision. An environment snapshot MAY contain bounded host, runtime, execution-location, locale, encoding, and resource-constraint information. It records state at its capture point and does not assert that the state remained unchanged for the execution duration.

The producer MUST NOT use `environment` as a general-purpose machine dump. Environment variables MAY be captured only when explicitly selected by the applicable capture configuration. Secret-bearing credentials, authentication tokens, private keys, and equivalent sensitive values MUST NOT be captured as environment observations. An absent environment value MUST NOT be replaced with an inferred, normalized, fabricated, or placeholder value represented as captured state.

Tool implementation identity is distinct from environment and, when recorded, belongs in `tool.implementation_digest` rather than `environment`.

## 4. Roles and completion

### 4.1 Artifact roles

N-002 defines these artifact roles:

* `supplied` — bytes delivered to the raw execution boundary.
* `stdout` — bytes observed on standard output.
* `stderr` — bytes observed on standard error.
* `file` — bytes captured from an execution-related file.
* `environment` — captured runtime-state bytes, subject to Section 3.2.

An artifact role records origin or relationship only. A record MAY include multiple artifacts of the same role when their distinct identity is preserved by surrounding record structure.

### 4.2 Completion facts

Completion facts, including `exit_code`, signal observation, and `timed_out`, are observations rather than classifications. In particular:

```text
exit_code = 0        != PASS
exit_code = 1        != FAIL
signal = SIGKILL     != REJECTED
timed_out = true     != UNRESOLVED
```

## 5. Conformance

An implementation conforms to N-002 when it preserves and records the required facts, uses the defined artifact representations, and applies the digest rule in Section 0.2. Conformance MUST compare recorder output with an independent byte vector and SHA-256 oracle; a successful process exit alone does not establish conformance.

The fixture suite is independent of qualification semantics. It MUST cover at least normal completion, non-zero completion, signal termination, timeout, zero-byte output, binary/NUL data, and transport round-tripping, including negative boundary checks.
